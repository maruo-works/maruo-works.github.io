このサイトの速さの点数が、66でした。PageSpeed Insights（Google の無料の測定ツール）の、スマホの値です。

## 点数66の原因は、2つだった

最初は「本番が遅い時間帯に当たっただけ」と考えました。翌朝も66。仮説は外れでした。

<Steps>
1. **画像が見つかるのが遅い**
   トップの大きな画像は、最初のHTMLにファイルの指定がなく、CSSを待ってから JavaScript が選んでいました。昼・夕方・夜の切り替えの判断をHTMLの先頭（head）に移し、先読み（preload）を足しました。見つかるまでの遅れは70msから21msに。
2. **日本語フォントが重い**
   CSS 61KiB（キロバイトの単位）に、字の範囲ごとの25ファイルを足して約590KiB。Google Fonts に「ページに出てくる184字だけ」と頼む（`text=`）と、約100KiBになりました。見た目は同じです。
</Steps>

## 86まで上がって、残りは測り方の差だった

公開後の点数は、66から86。最初の描画は5.1秒から2.7秒、いちばん大きい要素が出るまでは5.6秒から3.2秒になりました。画像の画質も下げて87。ここで打ち止めにしました。

なぜ100にならないのか。点数を出す Lighthouse は、遅いスマホを想定します。回線は1.6Mbps・往復150ms、処理は4倍遅い。しかも実際に遅くして測るのではなく、一度測った結果から「遅かったらこうなる」と計算します。

実験で、フォントを止めて測ると96になりました。でも、フォントを使わない本物のChromeでも、最初の描画は約1.4秒かかります。差はサイトではなく、測り方に出ていると判断しました。

    いちばん大きい要素が出るまで、4分の3の訪問で1.27秒以内（中央値は0.53秒）。Google の「良好」の基準、2.5秒以内に収まっている。

本物の数字は、Cloudflare Web Analytics（cookie を使わない解析）の直近24時間です。ほとんどが自分の確認の訪問なので、参考値です。

## 点数で探し、本物の数字で止める

| 見るもの | 向いていること |
|---|---|
| 点数（ラボ） | 直す場所を探す。直す前後を比べる |
| 本物の数字（フィールド） | 直し続けるか、止めるかを決める |

今回、点数を追うのをやめられたのは、本物の数字が良好だったからです。訪問はまだ少ないので、読んでくれる人が増えたら、もう一度見ます。

点数は、直す場所を教えてくれます。止まる場所は、本物のブラウザが教えてくれます。
